Form handling: the direction

Three concepts, clearly separated:

  • Field — thin wrapper: connects react-hook-form to the UI component
  • Layout — visual arrangement: label, errors, spacing, extra buttons
  • Controller — wires RHF state into Layout + Field via context

Layout and Field are separated so display can vary without duplicating field logic.

API 
<ControllerLayout name="field" rules={}>
  <Field />
</ControllerLayout>

Multiple layout variants out of the box:

  • ControllerGridLayout
  • ControllerVerticalLayout
  • Custom layouts via ControllerDefaultLayout

Part 2

General

The world has changed

The tools changed. The job is changing with them. We need to adapt.

  • Before: you were the agent
  • Now: you are the team lead of AI agents
  • Tomorrow: you are the product owner

The bottleneck moves from doing to specifying. You define the task — the agent handles the execution loop.

The only question is how fast you adapt.

Change mindset

Task-oriented

My goal is to close tickets

You receive a spec, you implement it, done. Success = task completed. This loop is exactly what AI is replacing — fast, cheap, tireless.

Product mindset

My goal is to deliver value

Success = real impact for the user and the business. Code is just one tool to get there. AI frees up time to think about the right problems, not just execute.

This isn't about doing more of the same. It's about becoming the product owner of your own feature pipeline.

The evolution of engineering work

STAGE 0 · HANDCRAFT

Written by hand. Speed came from experience and deep language knowledge.

STAGE 1 · AUTOCOMPLETE

Less memorisation, faster boilerplate. Speed came from delegation.

← we are here
STAGE 2 · AGENTIC AI ASSISTANT

Full features from descriptions. Agent owns the task end-to-end inside your session.

STAGE 3 · MULTI-AGENT

Sub-agents in parallel — each owns a stage, sees only what it needs. You orchestrate, they execute.

STAGE 4 · BACKGROUND AGENTS

Runs without you. No workstation needed — define the goal, agents handle the rest while you sleep.

Specify. Review. Steer.

Without a harness, an AI agent is a thoroughbred in an open field. Fast, impressive, utterly useless for actual work.

  • Setting up the agent — CLAUDE.md, skills, rules, tools. What Claude knows about your project before it starts.
  • Adding task context — relevant files, examples, constraints, related tickets. The more the agent knows upfront, the less it has to guess.
  • Specifying intent — clear task definitions, acceptance criteria, what "done" means. Vague input → vague output.
  • Providing feedback — reviewing agent output, correcting course, teaching the system. Not debugging line by line.

Why Claude Code

What sets it apart
  • up to 1M token context — reads the entire codebase, not just open files. Fewer hallucinations, deeper reasoning.
  • Model + harness co-built — Anthropic made both. No adapter layer, no quality loss.
  • True agentic loop — reads files, runs commands, fixes failing tests, opens MRs. Not autocomplete, an autonomous worker.
  • Best for agentic tasks, ships features fastest — purpose-built for autonomous multi-step work, not an IDE plugin with agent mode bolted on. New capabilities land here first — others follow.
Honest cons
  • UX — terminal-first, no inline suggestions. Different paradigm from Cursor/Copilot. Takes adjustment.
  • Setup cost — CLAUDE.md, MCP servers, skills all need upfront work. Cold start is slow.
  • Token burn — large context = higher cost per session. Agent teams multiply this.

Essential MCPs

MCPs extend Claude's reach into your actual workflow — not just code.

  • Jira — read tickets, create issues, update status
  • Slack — search messages, post updates
  • Notion — read/write docs, specs, notes
  • Figma — read designs, extract tokens
  • Context7 — up-to-date library docs (avoids hallucinating old APIs)
  • Serena — token-aware codebase navigation, reduces context cost
  • RTK — AI agent toolkit (rtk-ai/rtk)
  • glab — GitLab CLI: MRs, pipelines, reviews
  • chrome-devtools-mcp — connects agent to a live Chrome tab: inspect DOM, read console logs, watch network, automate interactions. Full browser vision for agents where --chrome is unavailable

Run /mcp list to see connected MCPs and their auth status. Most require OAuth — authorize once per session.

Browser automation: --chrome

Claude can control a Chrome browser directly — navigate, click, fill forms, take screenshots, read the DOM.

  • UI testing without writing test scripts
  • Verify visual output after a change
  • Fill staging forms, test user flows
  • Screenshot capture for visual regression

Windows limitation: --chrome mode requires additional setup on Windows (Chrome debug port configuration). Works out of the box on macOS and Linux.

How we use it

Launch a local dev server → point Claude at it → describe what to check. Useful for catching layout regressions without writing Playwright specs.

Field-tested tips

  • Plan Mode — Shift+Tab twice. Read-only exploration until you confirm. Fewer wrong assumptions. Use /model opusplan to switch to Opus for the planning phase — better reasoning on complex tasks.
  • HANDOFF.md — before ending a session, ask Claude to write current state: what worked, what didn't, what's next. Fresh context picks up from there.
  • Define "done" upfront — which commands must pass, what screenshots should show. If you can't articulate it, the task isn't ready for autonomous run.
  • claude --continue — resume the latest session. --fork to try a different approach from the same point.

Setup once, benefit every run

An LLM is a pure function. Same model — but the output quality depends entirely on what you put in.

maximize  quality  =  f( context, prompt ) tokens  →  min
  • Context — what the model knows: your codebase, rules, task definition, available tools. Relevant context = better output. Noisy context actively hurts.
  • Prompt — how you frame the task. Garbage in, garbage out. Vague input → vague output, no matter how good the model.
  • Tokens — time × money. Every token in the window costs. Wasted context = wasted budget.

The goal isn't to give the model more — it's to give it exactly what it needs. As I covered in the previous talk: it's all about storytelling.

Five building blocks

Each solves a different problem. Don't mix them up.

BLOCK WHAT IT IS WHO TRIGGERS GOOD FOR
CLAUDE.md Persistent context the model reads at session start Auto-loaded Rules, conventions, "never do X"
Slash commands Stored prompts and multi-step procedures You, explicitly Recurring workflows you control: /commit, /review-pr
Skills Instructions + code bundled as a portable capability Claude, automatically Shareable domain knowledge: translate, markup, deploy
Hooks Shell scripts that run at specific lifecycle events Event-triggered, always Guaranteed side effects: lint, notify, log, gate
Sub-agents Isolated Claude instances with their own context window Claude spawns, or you explicitly Parallel work, large codebases, multi-step isolation

CLAUDE.md

A markdown file Claude reads at session start — your persistent instructions. The more it knows about your project and preferences, the less you repeat yourself.

  • Project architecture and conventions
  • Forbidden patterns ("never use X")
  • MCP setup and tool availability
  • Repo-specific commands and workflows
  • Links to key docs or specs
Override hierarchy
  • ~/.claude/CLAUDE.md — personal global defaults: your preferences, style, tools
  • ./CLAUDE.md — project conventions, committed and shared with the team
  • ./CLAUDE.local.md — your local overrides, gitignored
Pro tip

After fixing a mistake: "Update CLAUDE.md so you don't do this again." The agent maintains its own instructions.

Convention across all our projects: we proxy everything through AGENTS.md — one entry point regardless of the tool.

Tip: Don't overload — noisy context hurts results. Keep AGENTS.md compact. Use progressive resolve — module-level files for local context, root only for global rules. The agent reads the closest one first.

Slash commands

Stored prompts and multi-step procedures you trigger explicitly. From simple one-liners to complex workflows.

  • /commit — draft a commit message
  • /review-pr — review a pull request
  • /compact — compress context to save tokens
  • /model opusplan — switch to Opus for planning phase
  • /implement — spec → code → MR, your custom pipeline
Where they live
  • ~/.claude/commands/ — global, personal
  • .claude/commands/ — project, shared with team

If a skill isn't being auto-invoked reliably — wrap it in a slash command. You get explicit, predictable control.

Skills

Skills are all about automatic discovery. Bundles of instructions + code Claude finds and applies on its own. Best for single, well-defined tasks.

  • Markdown files in .claude/skills/, can include Python scripts
  • Claude invokes them when it detects a matching task — no explicit call needed
  • Operate inside the current conversation — no separate session, no isolation
  • Portable — work across Claude web, desktop, and Claude Code
  • Shareable — team gets the same capabilities via plugin registry

Auto-invocation can be inconsistent. For critical workflows — use a slash command instead for predictable control.

Skills vs Sub-agents
  • Skill — enhances the current session. Single task, no context isolation.
  • Sub-agent — separate worker, isolated context. Complex multi-step work.

A skill file is also an onboarding doc — a new team member reads the same file as the agent.

Hundreds of ready-made skills available to download. You can also grab skills from colleagues — just copy the file.

Agents (sub-agents)

A self-contained AI assistant with its own personality, knowledge, and tools. Claude can delegate to them automatically, but you can also tell it explicitly: "Use the debugger subagent to check this error". The right expert is always on the case.

  • Context management — offload heavy work (codebase search, doc review) without filling up your main session
  • Parallelism — spawn 10 agents researching 10 things simultaneously. All report back at once.
  • Specialisation — each agent gets only the skills and context it needs for its task
  • Sustained focus — complex multi-step work without distraction from the main session
  • Simple config — single markdown file with YAML frontmatter. That's it.
Rule of thumb

If you can describe "done" — an agent can get there

Ticket → spec → code → tests → MR → Jira comment. Each step is a task. The agent chains them.

Isolated context is a double-edged sword: good — clean window, no noise; bad — agent may lack knowledge it needs. Solution: put domain knowledge into skills. Skills travel with the agent.

Parallel agents burn tokens fast. Use for tasks that genuinely benefit from parallelism — not as a default.

Subagents vs Agent teams

Subagents
  • Spawned by main agent, report back to it only
  • Can't talk to each other
  • Lower token cost
  • Best for focused tasks where only the result matters
Agent teams EXPERIMENTAL
  • Teammates message each other directly
  • Shared task list — self-coordinating
  • Higher token cost, scales with team size
  • Best for parallel exploration, competing hypotheses, cross-layer work

Rule of thumb: if workers only need to report results — subagents. If they need to debate and coordinate — agent team.

Step one: teach the agent

AGENTS.md — the project map

A single comprehensive file with all conventions, structure, and rules. The agent reads it at session start — instant onboarding.

5 specialized skills — domain knowledge
  • analyze-requirements — parse any input (spec, Notion, raw text) into a structured plan
  • markup — implement templates using existing partials, never raw HTML
  • translate — 7 languages with typography rules (nbsp, French punctuation, plurals)
  • visual-review — open in browser, compare to spec, produce pass/fail report
  • deploy-to-test — commit, push, create MR, update Jira
What this gave us

The agent understood the project

Full awareness of conventions, file structure, build pipeline. No more hallucinating partials or inventing helpers. It knew what to do and how.

But this alone wasn't enough. Developers still had to run each step, review details, manage the flow. They didn't want to become email experts — they wanted to delegate the whole thing.

So we went further — a fully autonomous pipeline.

The idea: a purpose-built pipeline

Don't use Claude as a smarter autocomplete. Build a pipeline of specialized agents where each one owns a single stage.

  • Input can be anything: raw text, Jira URL, Notion spec
  • One command kicks off the whole flow
  • Human reviews the spec — not the implementation details
  • Agent handles the rest: markup, tests, visual QA, MR, Jira update
Command

/markup-email DEV-12345

or a Notion URL, or just a description — the orchestrator figures out the rest.

The agent fetches the Jira/Notion/Figma context itself. You don't copy-paste specs into the prompt.

Architecture: three agents + orchestrator

Agent 1

Planner

Reads the input (any form). Searches the codebase for similar templates, existing keys, partials. Produces a structured spec.

Makes autonomous assumptions, documents them. Uses Opus for complex analysis.

Agent 2

Markuper

Implements the spec: subject.hbs, content.hbs, context.json. Runs npm test and ESLint. Fixes failures automatically (up to 3 attempts).

Reuses existing partials. Simplicity first — minimal new code.

Agent 3

Reviewer

Opens the rendered email in a browser via MCP. Compares output vs. spec block by block. Produces a structured PASS/FAIL report with screenshots.

Read-only. Never modifies files.

A lead orchestrator (/markup-email) coordinates all three — fetches external context, gates at spec approval, runs deployment.

The pipeline end-to-end

  1. Orchestrator fetches spec from Jira / Notion / Figma via MCP
  2. Planner analyzes, searches repo, produces structured spec
  3. You review the spec — correct if needed
  4. Markuper creates 3 files + 7-language translations
  5. Runs npm test — fixes failures autonomously
  6. Reviewer opens browser, screenshots, compares vs. spec
  7. Orchestrator commits, pushes, creates GitLab MR, posts QA results to Jira
Your touchpoints

Two moments, not seven

1. Review the spec after Planner.
2. Merge the MR after everything passes.

How can you help?

The infrastructure is live. It gets better with every use.

Yes, it will hallucinate at first. The only way to fix that is to try it, find the gaps, and fix them.

Try it
  • Try Claude on a task you know well — without /implement. See what it can do out of the box.
  • Then run /implement DEV-XXXX on a real ticket. Notice the difference.

Nobody is forced to use /implement — use it when it makes sense. The goal is to have the option, not to replace your workflow.

Feed it back
  • Something broke or felt wrong — tell us. Every failure is a gap in a skill file.
  • Something worked better than expected — also tell us.
Suggest & add skills
  • You know your domain better than any skill file. If you spot a missing convention — propose it or write it.
  • A skill is just a markdown file. If you can describe how something should work, you can write a skill.

The goal: the agent knows the codebase as well as the most experienced dev on the team. That only happens if the team is involved.
